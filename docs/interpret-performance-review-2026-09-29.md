# 同声传译代码、测试审查与改进方案

日期：2026-09-29。范围：当前未提交改动及其调用到的既有播放、下载、缓存逻辑。

> 下文审查记录是修复前的历史证据；当前实施结果见文末“六、修复落地与验证”。原诊断脚本已改为执行正向回归测试。

## 结论与证据边界

当前不能用“单测全绿”证明同声传译可观看。新语义路径把多轮模型请求放进首声和补缓冲的关键路径，窗口内存在整批等待；原有声纹/缓存顺序、配音超时长暂停策略又放大了停顿。另有已复现的片段丢失与错误译文绑定，必须和性能一起修。

本次完成审查、离线故障复现及实施方案；新增诊断脚本，没有修改生产实现或原有测试。未连接用户正在观看的浏览器会话，未测量当前真实 LLM/TTS 的耗时，不能把以下结构性问题的贡献比例当成实机性能结论，也不能宣布播放已修好。

验证记录：

- `node scripts/run-tests.mjs`：73 个测试文件通过，62.1 秒。直接运行测试器，没有运行会重建 agent bundle 的 `npm test`。
- 同传相关筛选：24 个测试文件通过；另直接运行 `test_planned_interpret.mjs`、`test_interpret_startup.mjs`、`test_dub_sentences.mjs`、`test_dub_timeline.mjs`，通过。
- `node tools/diagnose_interpret_regressions.mjs`：离线复现下列缺陷。该脚本断言的是“现有问题存在”，不是修复后的验收测试；修复后应把相应场景迁入正式测试并反转断言。
- 对新增功能测试做故障注入：所有 fetch 失败，所有 TTS 请求永远不返回；结果仍是 **4 项通过、0 项失败，退出码 0**，实际进入了 2 次挂起的 TTS。
- 只读检查本地媒体缓存：一段 1368.601 秒视频有 338 条字幕，首条 37.136 秒开始，约 90.2% 没有句末标点；另一段 2282.027 秒视频有 882 条字幕，约 98.8% 无句末标点。这只是素材分布，不是服务耗时测量。

## 一、卡顿根因与放大因素

### P1：语义路径串行请求和整窗口交付，直接阻塞首声及补缓冲

位置：`extension/lib/planned-interpret.js:64`、`:143`、`:290`、`:343`、`:933`。

当前链路：

```text
切音频、算指纹
  → 全窗口都没句末标点时，先请求模型断句
  → 翻译一个批次（最多 15 个语义单位）
  → 对超预算句子逐句 await 模型压缩
  → 等窗口内所有批次完成
  → 才把结果放入待合成队列
  → 声纹提取 → TTS → 可播放
```

断句和每一次压缩的独立上限都是 20 秒。15 句全部超预算时，压缩一项的串行超时预算就可以达到 300 秒；这只是代码上限，不是已观测等待时间。翻译主请求还沿用 90 秒、最多 3 次的网络重试，另有两次格式尝试和逐句恢复。

**已复现**：3 条译文中前 2 条完全有效，只挂住第 3 条的压缩，TTS 调用数仍为 0，视频保持暂停；放行压缩后才出现 3 次 TTS。说明即便前句可用，也被后句质量处理拦住。

已有短首窗（12 秒）、预热后最多 15 单位的限制方向正确，但不能消除窗口内串行压缩及整批返回。不要把 600 秒翻译前瞻误读为每次一定翻译 600 秒；它当前是后台目标，预热窗口通常最多约 120 秒，并有单位数约束。

### P1：字数预算不能保证配音时长，现有同步策略会主动冻结画面

位置：`extension/lib/dub-timeline.js:239`、`extension/lib/planned-interpret.js:1277`。

`fitDub` 最多加速到 1.12 倍，最多借 1.5 秒空隙，剩下的超长语音靠暂停视频等它说完。已计算复现：4 秒时间槽内生成 8 秒语音，仍需额外暂停约 **3.143 秒**。若连续出现，就会表现为“播几秒、卡几秒”。这项策略原已存在，语义合并和译文变化可能增加触发频率，实机触发频率尚未测量。

新 `fitBudget` 只统计汉字，漏掉数字、英文专名等读音耗时；压缩结果只要不比原来更长就接受，不要求真的回到预算内。章节润色后也没有再做时长约束。现有测试返回一个“短”字，只证明调用了压缩接口，没有证明忠实性或可播时长。

### P1：缓存命中仍先做声纹提取，已准备的音频也可能等住

位置：`extension/lib/planned-interpret.js:775`、`:1022`、`:1058`。

完整计划启动会先预取说话人参考音；逐句生成也先提取参考音，再读 `stableAudioKey`。因此已有配音不代表可立即播放。此顺序为既有问题。

**已复现**：精确匹配、可读取的配音缓存已经存在，挂住声纹提取后，音频缓存读取次数为 0，视频暂停；释放声纹后直接命中缓存，TTS 调用数为 0。

新增失败候选次数限制有价值，但只限制次数，不限制等待时间；成功取得过参考音的未知说话人后续仍会做逐句提取。简单把所有未知说话人共用一个音色也不正确，应区分可靠说话人身份与未知身份。

### P1：后台说话人分析可能清空已经准备好的后续配音

位置：`extension/lib/planned-interpret.js:754`、`:792`、`:946`。

后台分析完成后，`refreshSpeakers` 删除当前播放截止位置后的 lines、ready、pending、coverage；正在翻译的旧 revision 结果也会被丢弃。于是可能在原本已有配音时重新翻译、重新合成，导致中途缓冲。静态代码确认该机制存在，尚未统计实际发生次数。机制原已存在，新链路重算成本更高。

### P2：有字幕也要等完整音轨下载；无字幕路径仍受整音轨准备影响

位置：`extension/lib/downloaded-audio-source.js:46`、`tools/media_helper.py:650`。

`openInterpretSource` 等媒体任务 ready 才返回字幕，而 ready 在完整下载、转 PCM 分段后才设置。“字幕优先免 ASR”并不等于“字幕先到先译”。下载重试从 2 次提高到 10 次也可能增加异常网络下的开播等待，不能解决上述生产队列问题。此项属于首次启动等待，与观看中反复暂停分开统计。

次要性能风险：字幕窗口仍切音频并把 PCM 字节展开成数字数组再 JSON 哈希；120 秒 16kHz 单声道 PCM 约 3.84MB，展开会产生更多临时数据。尚未证明它是界面掉帧主因，先打点，再考虑二进制哈希和去掉字幕路径无必要的音频读取。

## 二、新代码中的内容与时间轴问题

### P1：模型拆开的字幕片段在重新关联时丢失

位置：`extension/lib/dub-sentences.js:258`；`extension/lib/planned-interpret.js:56`、`:100`。

拆句产生 `a@0`、`a@5` 等片段 ID，但 `attachCueMembers` 只在原始 cue ID 表中查找。一个单位含“片段 ID + 完整 cue ID”时，片段找不到被过滤，完整 cue 仍保留，展开时不会回退到完整单位。

**已复现**：`hello world`（0–4 秒）与 `again`（4–8 秒），在字符 5 断开。翻译输入第二句为 ` world again`（约 1.818–8 秒），最终提交却变成 `again`（4–8 秒）。`world` 的源文追踪丢失，译文对应的起点被后移约 2.182 秒；字幕、配音及缓存都受影响。

修复必须让单位携带完整片段对象、原 cue ID、字符范围和 estimated 时间标记，不能用查不到就过滤的方式恢复来源。输出的来源文本与时间范围必须可追溯到输入。

### P1：错误 ID 的译文会被强行绑定；新测试的错误 mock 被这种宽松逻辑掩盖

位置：`extension/lib/dub-timeline.js:212`；`extension/lib/planned-interpret.js:298`。

单句 ID 会被强制改写；多句数量相同且每句至多一个 ID 时，也可能按位置重绑。恢复失败后还会取任意响应首句，或用原文当中文成功结果缓存。部分行为原已存在，新语义分支继续使用/复制。

**已复现**：原文 `The cost is ten dollars.`，模型返回 `ids:["unrelated"]`、译文“今天天气很好。”，被直接接收并绑定到当前句。自动检测所有语义错误不现实，但显式 ID 不匹配至少应被拒绝。

### P1：unknown 或字幕缺失被当成已知无台词

位置：`extension/lib/dub-timeline.js:43`、`:86`。

`knownQuietUntil` 可以从当前 unknown 区域直接推断到下一段 speech 前都安静；拼接 quiet span 时也没有拒绝中间空洞。已复现 unknown 0–10 秒被放行至 10 秒；music 0–2、music 10–20 两段被连接成截至 20 秒的 quiet 范围。

`subtitleLeadGap` 将字幕之间及最后一条字幕之后视为可跳过范围，没有与已知 speech 冲突时的仲裁。在稀疏或不完整字幕上，规划可能直接覆盖掉应该 ASR 的人声。没有字幕并不天然等于没有台词。

应区分 verified quiet、可信字幕轨明确覆盖的空档、unknown、识别失败。只有有证据且连续的 quiet 范围才能绕过等待；已知 speech 优先于“未找到字幕”。

### P2：术语状态只在一个窗口内有效

位置：`extension/lib/planned-interpret.js:350`、`:370`。

每次窗口翻译新建 glossary，priorLines 以空 terms 提交，而且已生成行的 terms 被删除。历史原文/译文有传递，但确认过的术语不会自然延续到下一窗口。应把历史与术语状态都归属到会话，随提交推进、随 seek/gap 明确重置或重建。

功能测试具体问题：

1. `--live`、`--mock` 写在说明里，没有实际解析；默认可能读取本地配置并发请求。
2. GET 根路径 200/404 只证明某个 HTTP 路由可达，未校验 ASR/TTS 协议，也未测试 Text LLM；报错后仍 `passed++`。
3. 所谓“真实视频”使用手写字幕、虚构 Blob、静态时钟，不读真实视频，也不真实播放音频。
4. 片头测试推进到 24 秒，首条台词从 25 秒才开始，关键边界未覆盖；`ttsSynthesized` 计数未断言。
5. 声纹用例只在片头等待约 200ms 后检查 sliceCalls 上限，没有要求处理满所有目标句、TTS 成功或出声；0 次工作也可能通过。其 analysis 从 10 秒开始，缺 0–10 秒，实际触发“时间轴存在缺口”回退。
6. `npm run test:interpret` 只执行这个功能诊断文件，不代表整个同传测试集合。

既有测试里有价值的“缓冲不足时暂停”“长配音说完后恢复”不应删除，但还应测累计暂停时长。验证系统有能力暂停，与验证观看体验良好，是不同验收条件。

## 四、建议代码方案与实施顺序

### 第一步：先封住内容错误并建立可测播放基线

1. 修复片段对象传递和不可丢失的来源映射；严格校验 ID、顺序、完整覆盖。只兼容明确的旧协议形态，不把显式错误 ID 强行改正。
2. 翻译失败作为独立状态（failed / fallback-original）向下游释放，不冒充成功译文，也不保存为完整成功计划；错误块不能永久占住队列。
3. 修复 quiet 连续性和 subtitle/speech 冲突规则。无字幕轨、稀疏字幕、完整字幕轨分别建模。
4. 语义模式保留可回退开关；在同素材 A/B 达标前不再把新默认当作已验证推荐。临时使用 cue 模式只能绕开新增断句/压缩链，无法修好既有缓存及超长配音问题。

### 第二步：让已确认译文尽早成为可播放音频

1. `prepareDubPlan`/`runSentenceTranslation` 增加异步批次产出接口（callback 或 async iterator）；校验完成的连续前缀立即交给 TTS，不等后句压缩和窗口末尾。
2. 关键路径按低水位优先规划小段。断句优先本地规则，模型辅助断句可与翻译合并请求；独立断句不能在每个无标点窗口前固定阻塞。保留残句上限与 speaker/overlap 约束。
3. 压缩改成对超预算句的受限批次修复，或后台处理尚未进入合成的句子；总重试预算按窗口/任务管理，取消“每句可各等 20 秒”的线性放大。前缀必须按顺序提交，不能乱序播后句。
4. 简报/章节润色为低优先级；缓冲低时不与紧急翻译争用模型配额。TTS 并发默认保持 1，只有确认后端支持且吞吐提高才增加。
5. 初始水位和续播水位分离，依据连续可播范围、实际生成耗时和播放倍速动态调整。3 秒开播与最多 10 秒续播目前是固定规则，不能保证抵抗一次长模型延迟；单纯继续降低水位会加重反复停顿。

### 第三步：缓存、声纹、分析都不能销毁可播库存

1. 先读稳定音频缓存并验证可播放；命中直接入 ready，不依赖本次声纹提取。缓存键必须包含真正影响声音的配置和版本，不能忽略声音身份变化。
2. 缺失音频时才取声纹；按可靠 speaker identity 缓存，并同时限制候选数与总耗时。配置参考音/中性音回退必须有明确策略，不能把另一位讲者音色借给未知讲者。
3. 后台分析采用前向生效：已提交、ready、已调度的片段保留；新的 speaker revision 只用于未提交区。对确需替换的远期片段先生成替代品再交换，不能先删后等。
4. 下载层分阶段返回字幕和媒体身份，让有字幕任务先翻译；音轨下载、声纹分析并行准备。保留完整下载实现作为兼容路径。

### 第四步：按实际配音时长闭环，避免逐句冻结视频

1. 记录原文槽长、译文字数、TTS 实际时长、允许加速后时长和预计 holdSeconds。按声音/模型的观测语速修正预算，汉字计数只作初筛。
2. 对超长音频最多进行一次有约束的重译/重合成；必须保留数字、否定、条件、专名，不能截音频或用删事实换时长。
3. 若生成吞吐长期低于播放消费速度，则任何有限缓冲都会耗尽。明确选择预缓存更长时间、切换更快服务，或有提示地回退到原声+已确认字幕；不要无限“播一小句、暂停很久”。阈值需实测后确定。
4. 完整离线生成模式可保留润色、较大上下文、充分修复；它的等待目标与同步观看不同，不应共享阻塞策略。

建议按“内容正确性 → 流水线交付 → 缓存/前向分析 → 时长闭环/下载阶段化”分成可单独验证的改动，分别更新相关缓存版本；无需清空所有用户历史缓存。

## 五、测试方案与完成标准

### 默认离线、确定性的回归测试

统一使用生产 `runPlannedInterpret`，注入可控时钟、模型/TTS gate 和会推进 currentTime、触发 ended 的音频模拟器。不要复制另一套窗口调度逻辑；等待某个状态/事件再断言，不依赖“睡 200ms 应该好了”。

必须新增：

| 场景 | 修复后必须成立 |
| --- | --- |
| 最后一句压缩挂起 | 前面已确认连续句能进入 TTS/ready，且保持播放顺序 |
| 已有精确音频缓存、声纹挂起 | 不调用声纹即可得到可播缓存；TTS 为 0 |
| 字幕内部拆分后与完整 cue 合并 | 文本、原始 ID、字符范围、时间范围完整；captions 与配音单位一致 |
| 模型重复 ID、缺 ID、错 ID、乱序 | 明确失败/修复，不能通过强制按位置重绑伪装成功 |
| unknown、quiet 断档、稀疏字幕覆盖 speech | 不误认静音、不漏过待识别人声 |
| 背景 analysis 晚到 | ready 库存不清空；无重复播、无当前句中途换声 |
| 片头到人声，再持续播放多个窗口 | 真正触发 Audio.play/ended，验证首声、续播及累计暂停，而不只看视频 play |
| TTS 慢、抖动、超时，2 倍速 | 水位按消费速度变化；等待有界，降级状态可观察 |
| 短尾句、长静音、用户暂停/拖动/停止 | 不等永远凑不齐的缓冲；无旧结果误播；取消不等请求完整超时 |
| 会话跨窗口的术语与预算修复 | glossary 持续有效；润色/压缩不破坏关键事实；不缓存失败译文 |

声纹测试需分别计数候选提取、音频切片、成功合成，等待指定数量目标句完成后再检查总上限。上下文测试除字段存在，还应核对 current 与 lookahead 来源不重叠、未来内容未提前提交。

### 服务联调与质量评估单独运行

- `test:interpret` 应覆盖离线同传测试集合；`test:interpret:live` 独立显式启用真实服务。解析并验证命令行参数；未配置应 SKIP，配置但失败应 FAIL。
- 联调使用合成的短测试音频调用真实 ASR 协议，用固定短文调用真实翻译和 TTS 协议，校验结构和音频解码、时长，日志统一脱敏。HTTP 根路径探活与协议验证分开报告。
- 质量评估分别采集 cue/sentence 模式的真实模型译文，固定素材、配置、缓存状态，再盲评忠实性、流畅性和术语。占位译文只留作结构测试，不能计算实际质量收益。
- 补充故障注入门槛：将 TTS 完全禁用、翻译永远挂起、所有服务断开时，相关成功验收测试必须失败；静音片头用例可独立成功，但不算整条同传成功。

### 实机性能记录与验收

固定同一组短句、无标点长句、快速访谈、背景音乐素材，各 3–5 分钟；分别冷/热缓存、1×/2×运行。至少记录：

- 点击到音源可用、首次译文、首次配音、首次真实出声；不能用片头原声恢复代替首声。
- 每窗口断句/翻译/压缩次数及耗时；声纹耗时；缓存命中耗时；TTS 生成耗时/产出音频秒数。
- 每分钟系统暂停次数、累计暂停比例和最长停顿；区分缓冲不足与配音超时长 hold。
- analysis 到达导致的失效/重算量、连续 ready 秒数、重复/遗漏/越界配音。

建议起始目标（待建立实机基线确认，不是本轮成绩）：精确缓存命中不受外部模型/声纹可用性影响；固定正确性样本无来源丢失/错 ID 接收；在平均产出快于消费的联调条件下，稳定阶段系统暂停占比不超过 2%，不反复出现超过 1 秒停顿。吞吐低于实时的配置应明确降级，不承诺这些目标。

只有生产路径回归、故障注入和同素材实机播放三者都通过，才能把语义模式重新作为已验证默认。


## 六、修复落地与验证

已完成生产实现和测试修正：

- 增量交付确认译文，首句不再等待整窗口预算修复；实时模式不再先调用模型恢复标点，新增配置默认使用 cue。跨窗口保留术语，拖动时重置上下文。
- 严格校验来源 ID，保留字幕内部拆分的字符范围和时间来源。错误译文明确标记失败，不回填原文冒充译文，不缓存为成功；压缩校验数字、否定、条件和专名，拒绝明显信息删减。该校验是保守启发式，不能代替真实翻译质量盲评。
- 精确音频缓存先于声纹提取；音频指纹直接哈希二进制。声纹提取限时，未知说话人提取连续失败后跳过，不借用其他人的声音。晚到的背景分析仅作用于后续内容，保留已就绪配音。
- 根据实际生成时长及播放倍速调整缓冲，短尾句不等待不可能达到的水位。TTS 和实时等待设上限；过长配音最多一次有限时长修复，仍无法跟上则保留原声和已确认字幕。完整翻译缓存同样遵守实时限制。显式 full/buffered 模式仍保留其等待准备行为。
- 区分已知静音与未知覆盖；完整字幕声明和分析证据用于判断静音。媒体服务有完整字幕即可先提供翻译输入，音频切片按需等待下载完成。补回合理的下载重试和网络超时。
- 缺译文、缺音频以部分完成状态交付，不生成成功归档；界面可显示缺口和部分完成。补充音源、缓存、声纹、翻译、TTS、首声和等待指标。
- 功能测试改为推进视频和音频两套时钟，直接运行生产调度器，验证 1×/2× 多窗口完整出声和暂停比例。修正错误 ID 自动接受、后台分析重做、借用未知说话人声音等错误断言。
- 服务测试默认离线；真实服务需显式启用。未配置 SKIP，已配置但协议/输出错误 FAIL；“全部服务失败”和“TTS 永不返回”不能获得功能验收通过。质量评估调用生产规划链路，占位输出只验证结构，禁止计入翻译质量评分。
