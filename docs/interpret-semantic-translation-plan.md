# 同声传译语义分段改造方案

日期：2026-09-11。状态：0.12.0 已实现下述首版范围，后文保留完整目标设计。

### 首版落地范围与待验证项

- 已实现按序 ASR 归并、零至多句输出、半句缓冲、模型分句与翻译合并请求、严格原文拼接校验、一次格式修复重试、前文及有界术语参考。
- 已接通开播不足一批时释放等待、积压处理、自然结束尾句、拖动状态清理、远端请求超时和 TTS 失败文字回退；移除输入/译文的静默截断，给新归档增加处理版本。
- 当前模型分句的完整前缀可含多句，并作为同一个配音单位；达到源跨度 15 秒或 1600 字符预算时，本地规则拆出句段。只有段级时间时标记估算，不假装精确对齐。
- 当前开播仍使用三条配音目标及部分批次放行；“按实际配音秒数设定 6–10 秒目标”留待真实声音延迟测量后调整。TTS 输出超过现有 500 字限制会走文字回退，不截断。
- 连续 PCM 环形缓冲、音频窗口重叠及去重属于第二阶段，本版未改动采音格式。内部 `runInterpret({ semanticTranslation: false })` 可在新会话进行旧分块流程对比；界面默认使用新流程。
- `interpret-sync.js` 当前没有生产调用入口，本轮保留，实际控制器调用 `runInterpret`。未来启用该入口前需要复用语义处理器。
- 自动化测试使用可控的识别、模型与音频响应验证流程；尚未用用户当前视频和真实服务测量语义错误率或 p95 延迟，不能把方案中的收益目标当成已经达成。
- 验证记录：16 组相关测试通过（语义、队列、同传流程、控制器、播放、ASR、语音质量、TTS、VAD、页面采音、多视频同传、模型接口、音轨合成、下载音源和日志等）。`test_video_concurrency.mjs:40` 的旧页面测试仍因 `state.interpret` 未定义失败，已在未修改的 HEAD 独立副本复现同样错误；本轮没有修改该页面逻辑。

## 1. 目标与判断边界

将翻译单位从“采音块”改为“语义完整的句段”，减少跨块否定丢失、指代错误、术语不一致、半句话被补写和重复配音，同时保持有界等待、可暂停、可拖动。

当前代码可以确认存在结构性风险，但尚未对照具体问题视频的声音、ASR 原文和译文，不能认定所有偏差都由断句造成。实施前保存同一段视频的基线日志，分别标记听错、分句错误、翻译错误和播放错位。

第一版覆盖现有音频同传路径；继续使用现有 ASR、文本模型和 TTS。不新增用户必须配置的服务。字幕来源、全文转写不在本轮替换范围；若同步播放入口仍可达，必须接入同一语义处理器，避免两条路径表现不同。

## 2. 已核实的现状

| 位置 | 当前行为 | 对设计的影响 |
| --- | --- | --- |
| `extension/lib/interpret.js` | `CHUNK_SECONDS = 5`；识别片段拼接后立即调用 `translateToZh` | 没有跨块句尾缓冲 |
| `translateToZh` | 仅发送当前原文，截到 800 字符，输出预算 220 tokens | 没有前文；合并长句后不能照搬截断策略 |
| `extension/lib/tab-audio-record.js` | 流采音可等待约 300ms 静音，默认最长约 7.5 秒；不可用时按时长切 | VAD 停顿不是语义边界 |
| `extension/lib/tab-audio.js` | 页面采音 `recordPageSlice` 按请求时长取块 | 不能假定所有采音路径都有 VAD |
| `extension/lib/interpret-pipeline.js` | 两路 preparation 并发，合并 ASR 与翻译；按入队顺序合成播放 | ASR 可并发，语义状态更新必须按源顺序 |
| 开播/背压逻辑 | 以音频块和待播条数计数，默认准备三段配音 | 改为一块产生零至多句后，需要重新设计完成条件 |
| `extension/lib/interpret-sync.js` | 另有逐块识别与翻译逻辑 | 落地时核实调用链并复用处理器 |

## 3. 目标流程

```text
连续采音 → 音频块 → 并发 ASR → 按序归并 → 语义缓冲
                                             ↓
                    前文与术语 → 完整句段 → 翻译 → 已确认译文
                                                        ↓
                                                   TTS → 播放
```

采音块、句段和配音段是不同对象：一块可以没有完整句，也可以产生多句；一句可以跨多块。不能通过扩大一个 `prepare()` 的返回值，继续假设输入输出一一对应。

第一版保留约 5 秒采音目标，先修复文本语义链路。第二版再做连续 PCM 环形缓冲和边界重叠，避免一次同时改动采音、识别和播放导致难以定位回归。

## 4. 数据与顺序约束

- AudioChunk：`runId, generation, chunkId, start, end, blob, capturePath`。
- AsrChunk：保留上述标识及带时间范围的 segments；结果状态区分成功、静音、失败，不能让失败的序号永久阻塞后续。
- Utterance：`utteranceId, generation, sourceChunkIds, start, end, sourceText, boundaryReason, forced, timingQuality`。
- Translation：绑定 `utteranceId`，保存原文、译文、上下文版本、术语版本和提交状态。

ASR 保持最多两路并发。完成结果进入按 `chunkId` 排序的暂存区，只有连续可消费的结果才交给语义缓冲。每个请求有有限超时；失败产生 gap 事件，清理跨缺口的半句，不把缺词的前后文假装拼成完整句。

第一版每个 generation 的翻译串行，以保证上一句已确认译文可用于下一句。ASR、翻译、TTS 和播放仍可彼此重叠；后续只有性能数据证明必要时才引入翻译并发。

所有状态按 runId/generation 隔离。提交边界单调向前，同一句最多翻译提交一次、合成一次、播放一次；重试复用同一个 utteranceId。

## 5. 语义缓冲与分句

每收到一块按序 ASR 结果，将文本追加到未提交缓冲区，输出零至多个已确认句段，保留末尾未完成部分。

边界判断采用两层：

1. 本地规则找候选边界：句末标点、较长静音、完整分句；保护缩写、小数、姓名、引号、括号。句尾为冠词、介词、连词，或疑似缺少宾语/否定作用对象时保留。规则只是启发式，不声称能准确解析所有英文。
2. 不确定时允许一次受限模型判断，与翻译合并请求以减少调用：提供前文和完整待处理文本，要求返回“可提交前缀 + 对应译文 + 原样保留的后缀”。必须验证前缀、后缀能逐字重建输入且提交点合法，不能接受模型改写原文或跨越缺口。无可提交前缀时继续等待。

明确边界直接走普通翻译，不对每块额外调用分句模型。结构化输出不依赖某个供应商专有接口；普通 JSON 返回也可校验。输出无效可修复重试一次，仍失败保留原文并等待或标记失败，不能把任意模型文本直接送去配音。

有界等待的初始调参值（均是设计起点，非已测得最佳值）：

| 参数 | 初始值 | 处理方式 |
| --- | --- | --- |
| 常规语义前瞻 | 优先等待下一块，约 5 秒源音频 | 当前句已完整则不额外等待 |
| 未提交源音频跨度 | 软上限 10 秒，硬上限 15 秒 | 优先在完整分句处拆；不能只按字符硬切 |
| 待处理文本 | 软上限 120 个英文词，硬上限 180 个词 | 尽早查找候选边界，异常输出先经过质量检查 |
| 模型判断/翻译超时 | 初始 15 秒，可配置 | 记录失败并有限重试，不无限占用序号 |

源音频时间、页面媒体时间和墙钟时间分开记录。上述语义跨度不等于用户实际等待时长；还要加识别、翻译和排队耗时。用户暂停期间不因墙钟到期擅自提交半句。

达到硬上限仍无完整边界时：只输出已经确定的最小分句；若仍是不完整片段，保守翻译可确定部分，明确禁止补全未说出的结论，标记 forced 并允许该次不配音。消费必须有进展，残余状态有界，并在日志记录舍弃或未能配音的范围。不能把“强行产出一句通顺中文”作为兜底。

## 6. 上下文、术语与翻译约束

每次请求区分三部分：最近三句已提交英文与中文、当前待译句段、必要的未提交后文。上下文总量初始限制为约 1500 字符；按完整旧句淘汰，不从句中截断。后文只用于理解，不允许提前输出。

提示词要求：

- 忠实保留否定、条件、比较、数量、因果与不确定语气。
- 不重复翻译上下文，不添加解释，不猜测缺失事实。
- 仅输出指定当前部分；遇到残句不擅自补出主语、宾语或结论。
- 专名不确定时保留原名。术语优先遵循已确认映射。

会话内维护有界术语表，初始最多 50 项。候选译法不能凭第一次猜测锁死；记录来源，允许后续证据修正，并仅作用于尚未提交的译文。页面标题可作弱背景，不能替代音频证据。

移除当前静默截取原文前 800 字符的做法，改为上游有界分句。输出预算根据输入长度计算并设上限；如接口返回截断原因则检测，未返回时只能使用启发式检查，不能声称能完整识别截断。截断或明显缺失则拆分重试，失败译文不进入 TTS。

前文必须从按序提交的状态快照读取，不能让并发完成顺序决定上下文。拖动或换视频清空上下文；识别缺口清理未完成语义，并标记后续上下文不连续。

## 7. 时间轴与声音参考

跨块句段使用实际覆盖的 ASR 时间范围，保留来源块列表。一个 ASR segment 内拆出多句时：优先使用服务提供的词级时间戳；只有段级时间时，按文本长度估算并标记 estimated，或保留为一个配音单位。不能把估算当作精确口型同步。

TTS 参考声音仍取该句来源范围内质量合格的样本，无需拼接整句音频。重用现有质量评估与参考音回退。配音过长时使用现有有界调速/等待策略，优先在翻译前拆分完整分句，不删词或截断已合成语音追赶画面。

## 8. 队列、开播与控制状态

拆为两级队列：上游有界 ASR 队列与语义状态；下游以 Utterance 入队，负责翻译、TTS 和播放。容量按阶段分别计算，同时监控未处理源音频秒数与可播放配音秒数，不能只用“三条”代表相同缓冲量。

开播初始目标建议为至少一条完整配音、累计约 6–10 秒可播音频，设有限采集预算。短视频、静音或尾批不足时允许部分缓冲启动。具体阈值通过基线对比调整。

必须解除循环等待：

- 语义缓冲需要后文时，不能因为已经采够三块就长期暂停画面等译文。
- 系统等待期间允许有界继续取声；当前页采音需要短暂恢复页面以取得后文。独立音源可按其现有能力继续预取。
- 达到采集预算则执行语义 flush/降级，启动已有配音或报告本段无法生成，不能永远等待“凑齐三条”。
- 背压暂停取声前，先将可提交分句释放给下游；未提交句尾不算可播放工作，不可占着容量等待自身释放。
- 播放缓冲目标按实际音频时长统计。TTS 失败时字幕仍提交，并让等待方收到完成/失败事件，不能永久等声音。

| 事件 | 语义与播放处理 |
| --- | --- |
| 用户暂停 | 冻结后续取声和播放；保留当前 generation 的半句，不因暂停强制翻译 |
| 同位置恢复 | 继续补齐半句；按源时间检查是否连续 |
| 系统背压暂停 | 消化已确认内容；需要后文时走有界取声状态，避免死锁 |
| 拖动/换视频 | 新 generation；清空未提交尾句、排序缓存、上下文、待播译文并取消旧请求；旧结果不得回流 |
| 视频自然结束 | 等最后 ASR 结束，显式 `flush(end)`，提交可译尾句，再排空 TTS 和播放 |
| 用户停止 | 立即取消，不补译残句；保留已提交内容 |
| ASR 失败 | 有限重试后记录 gap，不跨缺口拼句；继续后续序号 |
| TTS 失败 | 显示已确认译文，跳过该句声音并继续 |

拖动时正在播放的旧语音也需要停止；当前 `flushAhead()` 有保留正在播放段的语义，实施时必须通过播放控制层明确处理，不能只清队列。

## 9. 第二阶段：采音连续性与重叠识别

在文本链路验收后，为当前页和流采音统一增加连续 PCM 缓冲，以样本索引定义范围。相邻识别窗口可重叠约 0.5–0.8 秒，降低边界切词风险。

不能直接拼两个 WebM Blob，也不能依靠反复重新启动录音器实现可靠连续音频。先核实各采音路径的连续性和缓冲消费规则，再修改读取窗口。

重叠范围只作为 ASR 上下文，不重复生成句段。去重结合源时间和相邻边界 token 对齐；没有可靠匹配时保留不确定状态，不能全局删除重复词，否则会误删 `very, very important` 等真实强调。已提交原文不因新窗口重识别被悄悄改写。

## 10. 文件改动与实施顺序

| 阶段 | 改动 | 交付门槛 |
| --- | --- | --- |
| 0：建立基线 | 用现有 debug 日志保存固定视频片段、模型配置及采音路径；核实同步入口调用链 | 能对齐音频、原文、译文、播放时间 |
| 1：语义核心 | 新增 `interpret-semantic.js`：按序归并、句尾缓冲、边界判定、flush/reset；新增 `interpret-context.js`：前文与术语；调整 `translateToZh` 输入协议和校验 | 跨块否定/残句案例不漏词、不重复提交 |
| 2：完整接线 | 调整 `interpret.js`、`interpret-pipeline.js`，按需接入 `interpret-sync.js`；修正开播、背压、尾批、拖动、归档 | 可变输入输出数量下无死锁、无旧结果回流 |
| 3：采音边界 | 调整 `tab-audio-record.js`、`tab-audio.js` 及实际页面采音实现；`asr.js` 保留可用时间/置信信息 | 音频连续性、重叠去重测试通过 |
| 4：验证与发布准备 | 同视频对照、统计延迟、更新 README 与 CHANGELOG | 质量改善达到门槛且控制功能不回归 |

阶段 1 和 2 合起来才是可用的首版，不能仅改提示词就宣布解决。阶段 3 解决边界听错，可独立验证收益。

新旧模式用内部开关控制，开关变化从新会话生效，支持整条链路回退。异常时不要在同一会话中静默切回逐块翻译，以免重复消费。历史字幕/归档维持旧字段可读，新增字段可选；新缓存标记处理版本，避免读取旧译文误判新方案效果。

## 11. 可观测性与验收

新增事件：`asr.ordered`、`asr.gap`、`semantic.buffer`、`semantic.commit`、`semantic.flush`、`translation.context`、`translation.validation-error`。贯穿记录 generation、chunkIds、utteranceId、源时间、边界原因、强制提交标记与各阶段耗时。复用现有本地日志，不另建上传服务。

必要自动化测试加入现有 `extension/tools/test_*.mjs` 体系：

1. `I don't think / this is a good idea.` 跨块；`not only / but also`；条件、数字比较和代词指代。
2. `Dr. Smith`、`3.14`、引号内标点和 ASR 在残句末尾误补句号。
3. 一块零句、一块多句、一句跨三块；持续长句触发预算；自然结束残句。
4. ASR 乱序、超时、失败、静音；翻译非法 JSON、截断、重试；TTS 失败。
5. 已提交句不重复；真实重复词保留；重叠窗口边界对齐。
6. 开播尚无完整句、只剩一条配音、背压时有半句；暂停/恢复/倍速/拖动；旧请求迟到。
7. 合并句时间范围、估算时间标记、字幕和归档一致、声音参考可用。

真实视频评估至少覆盖清晰短句、技术长句、快速访谈、含背景音乐的语音，每类约 3–5 分钟；固定模型、视频位置、倍速和设置。人工逐句对照声音与原文，统计语义偏差率（否定、数量、指代、漏译和臆补）、重复/遗漏、首次出声、稳定期延迟 p50/p95、停顿占比和请求成本。

建议验收目标（需要基线后确认，非现有成绩）：

- 固定回归案例中无重复提交、无丢弃已确认句、无跨 generation 回流、无无限等待。
- 人工标记的“跨块造成的明显语义错误”比旧版减少至少 50%；同时报告样本数与 ASR 错误，避免把样本波动当收益。
- 稳定期新增端到端延迟 p95 初始预算不超过一个采音周期（约 5 秒）；超出则继续调整缓冲与请求策略，不直接默认开启。
- 首次出声和等待占比单独评估，不能用稳定期均值掩盖开播长时间卡住。
- 所有阈值、失败范围和质量改进附实际测量；第一版不承诺零延迟或口型同步。

## 12. 推荐决策

先落实“按序 ASR → 半句缓冲 → 带前文翻译 → 完整句配音”，同步重做开播/背压完成条件。第一版默认只展示已确认中文字幕，避免修订字幕带来跳动；未完成时仅显示“正在听取下一句”。

完成固定案例与真实视频对照后，再决定是否启用连续采音重叠，以及最终采用的等待阈值。交付应包含代码、针对性回归测试、同视频质量与延迟对照记录和可回退开关。
